# 架构设计

## 1. 总体架构

```
┌──────────────────────────── 入库（离线，分钟级） ────────────────────────────┐
│                                                                            │
│  data/raw/*.md|txt|pdf                                                     │
│        │ document_loader（清洗：BOM/空行/行尾空白）                          │
│        ▼                                                                   │
│  LoadedDoc 列表                                                            │
│        │ chunker（三策略：fixed / recursive / sentence）                    │
│        ▼                                                                   │
│  Chunk 列表（稳定 ID：source::序号，携带所属标题）                          │
│        │ embedder（bge-base-zh-v1.5, GPU, L2归一化）                        │
│        ▼                                                                   │
│  FAISS IndexFlatIP + metas.json + chunks.jsonl 落盘                        │
└────────────────────────────────────────────────────────────────────────────┘

┌──────────────────────────── 问答（在线，秒级） ─────────────────────────────┐
│                                                                            │
│  用户问题                                                                  │
│    ├─► 稠密检索：embed(问题+指令前缀) → FAISS top-20                       │
│    ├─► 稀疏检索：jieba分词 → BM25 top-20                                   │
│    │        │                                                              │
│    ▼        ▼                                                              │
│   RRF 融合排名（1/(60+rank) 求和）                                         │
│        │ reranker（bge-reranker-base 交叉编码器，GPU，逐对精排）            │
│        ▼                                                                   │
│   top-5 片段（含来源/标题/各路分数）                                        │
│        │ llm（OpenAI兼容 API / 抽取式回退）                                 │
│        ▼                                                                   │
│   带编号引用的回答 + 各阶段耗时                                             │
└────────────────────────────────────────────────────────────────────────────┘
```

## 2. 关键设计决策

### 2.1 为什么是"两级漏斗"而不是一级检索到底

| 环节 | 模型 | 候选量 | 耗时量级 | 特点 |
| --- | --- | --- | --- | --- |
| 召回 | 双塔 embedding + BM25 | 20+20 | 毫秒 | 快而粗，可离线建库 |
| 精排 | 交叉编码器 | 20 对 | 数十毫秒 | 慢而准，必须逐对在线算 |

交叉编码器精度高但无法预建索引，只能放在最后一步对少量候选精排。这是向量检索领域的标准工程结构。

### 2.2 为什么混合检索

两路召回的错误类型互补：

- 向量检索：懂语义改写（“挂科” ≈ “不及格”），但对课程代码、数字、专名不敏感
- BM25：术语精确命中极稳，但不懂同义表达

RRF 只用排名不用分值，规避两路分数量纲不可比的问题，是无训练融合的标准做法。

### 2.3 分块为什么是 recursive 而非固定窗口

固定滑窗会把句子拦腰截断，被截断的块向量表达失真。recursive 按"标题 → 段落 → 句子 → 分号逗号”的层级寻找天然边界，块内语义完整。这本身也是实验 A 组的对比对象。

### 2.4 为什么相关性判在"来源文档级"

不同实验的分块策略不同 → 块 ID 不同。若判块级相关性，标注随策略失效。"答案在哪个文档"是稳定的人工事实，跨策略可比——这是让四组实验公平成立的前提（代价是指标偏宽松，故辅以 MRR 拉开区分度）。

### 2.5 为什么 FAISS 用 IndexFlatIP 而非近似索引

数千级向量精确检索 <10ms，近似索引（IVF/HNSW）的收益为零还引入召回损失与调参成本。规模涨到百万级时再换，接口不变。

### 2.6 无 API 回退（extractive 模式）

未配置 LLM Key 时系统不报错，直接把 top 片段整理成带引用的草稿。价值：(a) 无 Key 也能全链路联调演示；(b) 充当"纯检索"基线，量化 LLM 生成的增量。

## 3. 模块依赖图

```
config（全局单例，env 重定向）
   ▲
   ├── document_loader ──► chunker
   │                          │
   ├── embedder ──────────────┤
   │                          ▼
   ├── vector_store ◄── retriever（依赖 jieba/rank_bm25）
   │                          │
   ├── reranker ──────────────┤
   │                          ▼
   └── llm ──────────────► pipeline（编排 ingest/load/query）
                              │
                              ├── scripts/（CLI：入库/问答/实验）
                              ├── app/web_ui.py（Gradio）
                              └── evaluate（指标计算）
```

约定：所有模块 `import config` 必须先于 transformers 系 import（HF_HOME 重定向才生效）；模型与索引等重型资源只在 RAGPipeline 进程内初始化一次。

## 4. 已知局限与演进方向

1. **语料规模**：全量重建索引的设计在万块以下最优；更大规模需要增量更新或换近似索引。
2. **多轮对话**：当前是单轮问答；可加历史改写（把“那实习呢”补全为独立问题）。
3. **表格/图片**：Markdown 表格以纯文本切块，结构信息损失；PDF 扫描件不支持（无 OCR）。
4. **评估规模**：30 题人工评测集，规模适中但可扩展为多标注者 + Kappa 一致性检验。
